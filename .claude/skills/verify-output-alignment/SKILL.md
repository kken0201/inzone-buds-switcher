# 出力の切り替えのモデル検査

## 何を確かめているか

- **性質**：イヤホン・ドングル・利用者・自動更新による再起動がどんな順序で起きても、外からの操作が止まれば、接続状態はイヤホンの実際の状態に一致し、既定の出力はそれに合ったデバイスに落ち着く。その途中で、確定していない状態で出力を変えたり、利用者が選んだ出力を上書きしたりしない
- **破れたときの害**：イヤホンをケースに戻したのにスピーカーから音が出ない、または使っているイヤホンから急に音が消える。利用者には原因が分からない

検査は `src/app/model.rs` にある Rust のテストで、追加の道具は要らない。本物の `App`（`state::Machine` と `switch` を含む）を、周りの世界を手で模したモデルの上で動かし、起こりうる順序を有限の範囲ですべて試す（幅優先の網羅探索）。

検査するのは次の 3 つ。

| 種類 | 内容 | 報告の見出し |
|---|---|---|
| 安全性 | `App` が出力を変えるのは `Transition::Changed` / `Established` のときだけで、変えた先の向き（ドングルかどうか）が接続状態と合う。`Established { connected: true }` でドングルのデバイスを上書きしない。切断したときにドングル以外のデバイスを上書きしない | `[安全性]` |
| 収束 | 外からの操作が止まったあと、内部の処理（`App::handle` / `tick`、デバウンスの確定、問い合わせの応答など）だけでたどり着く状態の集まり（出口のない強連結成分）がすべて `aligned` を満たす | `[収束]` |
| モデルの前提 | `App` が、モデルの `Key` から組み立て直せない状態になっていない | `[モデル外]` |

## 対象のコードと同期したコミット

手で模している部分（変えたら `src/app/model.rs` を合わせ直す必要がある）：

| コード | モデル（`src/app/model.rs`） |
|---|---|

## 既知の発見（`863c4bd` のコード）

検査は次の 2 つを見つけている。テストはこれらが残っていることを期待しているので、直したら期待を書き換える（後述）。

1. **`MissedCaseIn`**：接続中に両耳をケースに戻したときの `12 01` が届かないと、Connected のまま戻らず、既定の出力も Game のまま残る。両耳がケース内だとどの問い合わせにも応答がない（protocol.md 2 章）ので、30 秒ごとの `41 04` では追いつけない。docs/design.md 4.1 が問い合わせを足した理由（取りこぼしても追いつく）は、接続の向きにしか効いていない。例：
   1. イヤホンを出したまま起動し、Game に切り替わる
   2. 両耳をケースに戻すが、`12 01` が届かない
   3. 以後、`41 04` に応答がなく、状態が変わらない（スピーカーから音が出ない）
2. **`StalledAtOpen`**：ドングルを開いたときに `41 02` の送信がタイムアウトすると、`silence_deadline` が設定されず、問い合わせにも応答が来ないので、イヤホンを出し入れするまで Unknown のまま切り替えない。「状態が不明なときは何もしない」方針どおりだが、その間に Windows が既定の出力を Game にしていると、ケース内のまま音が出ない

## 結果の読み方

失敗すると、違反ごとに最大 3 件、初期状態からの最短の手順が出る。手順の各行は `Act::describe` の文で、コードの操作に 1 対 1 に対応する（「メインスレッドがイベントを 1 件 App::handle する」は `Tray::drain` の 1 回の `handle`）。

本物の不具合かモデルの誤りかは、次の順で見分ける。

1. 手順を `src/app/scenarios.rs` のシナリオテストに書き直して、本物の `App` で同じことが起きるか確かめる。`Act::Drain` は `App::handle`、`Act::Deadline` と `Act::Tick` は確定時刻での `App::tick`、`Act::User` や `Act::Unplug` は偽物の再生デバイスの書き換えにあたる。起きれば本物の不具合
2. 起きない、または手順の中に現実には起きない一歩がある（下の「前提と範囲」に反する）なら、モデルの誤り。`src/app/model.rs` のその操作を直す
3. `[モデル外]` は、`App` が `Key` で表せない状態になったことを表す。意図した変更で `App` に切り替えに効く状態が増えたなら、`Key` と `Sim::try_from_key` に足す。そうでなければ、状態機械を壊した可能性が高い（たとえば `Machine::observe` が確定済みと同じ値の確定待ちを残すと、これが出て、収束の違反も出る）

性質を弱めて通してはいけない。違反は、直すか、ここに既知の発見として書いて利用者に伝える。

## 意図した変更に合わせて直す

- **既知の発見を直した**：該当するテストの期待を `Some(Finding::…)` から `None` に変え、`Finding` から消し、上の「既知の発見」からも消す。直ったのに期待を変えないと「見つからなくなった」で失敗する
- **HID 監視スレッドやトレイの処理を変えた**：上の表で対応する `Act` と `Sim::enabled` / `Sim::step` を合わせる
- **`App` に切り替えに効く状態を足した**：`Key` に足し、`Sim::try_from_key` でその状態を作る手順を足す。`key_captures_app_state` が通ることを確かめる
- **設定項目を足した**：モデルは既定の設定（`auto_switch` オン、`connected_device` 未設定、`switch_communications` オフ）で動かしている。新しい項目が切り替えに効くなら、その値ごとに探索するか、範囲外としてこのスキルに書く

直したら、壊した変更（たとえば `switch.rs` の `on_established_connect` で `plan.default = Err(Skip::OnDongle);` を消す）で検査が失敗することを一度確かめてから戻す。

## 同期したコミットを進める

対象のコードが変わったら、検査が新しいコードを表していることを確かめてから（上の表の手で模した部分を読み直し、テストが期待どおりになることを確かめてから）、「同期したコミット」をそのコミットに書き換える。確かめていないのに進めてはいけない。

## 前提と範囲

通っても保証されるのは、次の前提と上限の中だけ。

- **上限**：イヤホンの出し入れ 3 回、ドングルを抜く・挿す各 1 回、利用者の手動の切り替え 1 回、再起動 1 回。外からの操作でチャネルに積めるのは 2 件まで（`BUDGET` / `CHANNEL_CAP`）
- **時刻**：デバウンスの確定時刻を過ぎたかどうかだけを区別する。どの間隔も任意に長くも短くもなりうるとみなす
- **一歩とみなすもの**：`App::handle` 1 回、`App::tick` 1 回。`App::switch` の中の「一覧と既定の取得 → 設定」は、その間に利用者や Windows が出力を変えないとみなす（実際は不可分ではない）
- **HID**：`41 02` の応答は開いた直後に届き、その間のイヤホンの出し入れは入れない。`41 04` は前のイベントを処理し終えてから届く（30 秒ごとなので）。左右は区別せず「どちらかが出ている」だけを扱う。ドングルのレポートは送られた順に届き、送られた時点の状態を表す
- **再生デバイス**：スピーカーとモニターは常にある。既定の通信デバイス（`switch_communications`）は扱わない。`set_default` の失敗は、デバイスが消えたときだけ
- **入れていないもの**：バッテリー低下の通知、トレイの表示とメニューの操作、自動更新のダウンロードと置き換え、スリープからの復帰、設定ファイルの保存の失敗

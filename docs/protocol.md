# INZONE Buds ドングル HID プロトコルメモ

実機（INZONE Buds、ファームウェア 02.000.006 と 03.000.004、INZONE Hub 1.0.20.0、Windows 11）で `probe` サブコマンドを使って確認した内容をまとめる。特に断りがなければ、どちらのファームウェアでも同じだった。実機で確認していない内容には「未確認」と書き、出典を添える。

## デバイス

| 項目 | 値 |
|---|---|
| Vendor ID | `0x054C`（Sony） |
| Product ID | `0x0EC2`（INZONE Buds USB トランシーバー） |
| HID インターフェイス | `MI_05`。5 つのコレクションを持つ（下表） |
| 再生デバイス | `MI_03` が「スピーカー (INZONE Buds - Game)」、`MI_00` が「ヘッドセット イヤフォン (INZONE Buds - Chat)」 |

トランシーバーのスライドスイッチは **PC** 側にしておくこと。

### HID コレクション

| COL | usage_page:usage | 入力 / 出力 / Feature（バイト、レポート ID 込み） | 用途 |
|---|---|---|---|
| 01 | `FF13:0001` | 62 / 62 / 0 | 不明。観測中にレポートは届かなかった |
| 02 | `000C:0001` | 2 / 0 / 0 | コンシューマー制御（メディアキー） |
| 03 | `FF04:0001` | 64 / 64 / 0 | **このアプリで使う**。状態・バッテリーのレポートと問い合わせ |
| 04 | `FF03:0020` | 0 / 0 / 35 | 不明（Feature のみ） |
| 05 | `FF01:0020` | 8 / 0 / 0 | 不明。観測中にレポートは届かなかった |

以下はすべて `FF04:0001` のレポート。オフセットはレポート ID（`[0]`）を含めて数える。

## 共通の形式

```
[0]  02          レポート ID
[1]  長さ?       種類ごとに固定（状態 0x0E、バッテリー 0x12 など）
[2..3] 04 FF     受信。送信では 01 00
[4]  長さ?       受信では [1] - 3
[5]  00          送信では 08
[6..7] 96 C3     固定
[8]  種別        受信：0x12（状態）/ 0x14（それ以外）。送信：0x41（問い合わせ）
[9]  サブコマンド
[10] 0xA0 = 自発送信、0x10 = 問い合わせへの応答。送信では 0x01
[11] シーケンス番号。応答では要求と同じ値、自発送信では 0x00 か 0x01
     （0x20 のもの（`14 87`）も観測した。意味は不明）
[12] 00
...  本体
末尾 チェックサム：[6] から直前のバイトまでの和の下位 8 ビット
```

チェックサムの規則は、受信した 5 種類のレポートと問い合わせの要求のすべてで成り立った。[1] / [4] の意味は推測。

## 1. 状態レポート `12 01`（自発送信）— 接続/切断の検知に使う

イヤホンを出し入れすると、ドングルから自発的に届く。問い合わせ（`41 01`）には応答しない。

| オフセット | 値 | 意味 |
|---|---|---|
| `[8]` `[9]` | `12 01` | 状態レポート |
| `[13]` | `00` / `01` | 左イヤホンが接続していれば `01` |
| `[14]` | `00` / `01` | 右イヤホンが接続していれば `01` |

例：`02 0E 04 FF 0B 00 96 C3 12 01 A0 00 00 01 01 0E`（両耳接続）

- 片耳ずつ出し入れすると、そのたびに 1 件届き、左右の値が独立に変わる
- ケースから取り出したときは、`14 02` → `14 03` → `14 04` のあと、約 0.4〜2.7 秒遅れて `12 01` が届く
- ケースに戻したときは、`12 01` が先に届き、そのあと `14 02` / `14 03` / `14 04` が届く
- INZONE Hub の起動中も、終了後も届く
- 操作してからレポートが届くまでの遅延は測っていない（操作した時刻を正確に記録する手段がないため）
- **届かないことがある**：ファームウェアを更新した直後、ドングルを抜き差しするまでの約 8 分間、出し入れしても自発送信のレポートが 1 件も届かなかった（問い合わせには応答し、INZONE Hub の表示は変わっていた）。原因は分かっていない。このため、自発送信だけに頼らず、定期的な問い合わせ（`41 04` など）でも状態を確かめる

## 2. 問い合わせ（送信）

64 バイトの出力レポートを `WriteFile` で送る。

```
02 0C 01 00 FC 08 96 C3 41 <sub> 01 <seq> 00 <sum> 00 ... 00
```

`<sum>` は共通のチェックサムで、`0x9B + sub + seq` と同じ値になる。

| sub | 応答 |
|---|---|
| `01` | 応答なし |
| `02` | `14 02`（接続とバージョン） |
| `03` | `14 03`（ファームウェアのバージョン） |
| `04` | `14 04`（バッテリー） |
| `21` | `14 21`（不明） |
| `41` | `14 41`（不明） |

- 応答は約 0.2〜0.4 秒で届く
- **両耳ともケースに入っていると、どの問い合わせにも応答しない**。INZONE Hub もこの状態では何も表示しない
- 応答は自発送信と同じ形式で、`[10]` が `0x10`、`[11]` が要求のシーケンス番号になる点だけが違う
- **応答は、そのコレクションを開いているすべてのハンドルに届く**。INZONE Hub が送った問い合わせへの応答も、こちらに届く。自分の要求への応答かどうかは、種別とシーケンス番号で判定する（Hub も小さいシーケンス番号を使うので、番号が重なることはある）
- INZONE Hub はイヤホンの接続時に、`12 09`、`14 06`〜`14 08`、`14 85`〜`14 8D` など、ここに載せていない問い合わせも送っている。どれも意味は調べていない

## 3. `14 02` 接続とバージョン — 起動直後の接続状態の取得に使う

| オフセット | 値 | 意味 |
|---|---|---|
| `[19..25]` | ASCII 7 文字 | USB トランシーバーの値と思われる。常に入っている |
| `[27..33]` | ASCII 7 文字 | 左イヤホンの値。未接続なら `0000000` |
| `[35..41]` | ASCII 7 文字 | 右イヤホンの値。未接続なら `0000000` |
| `[43]` | `01` / `FF` | 左イヤホンが接続していれば `01` |
| `[44]` | `01` / `FF` | 右イヤホンが接続していれば `01` |

両耳が接続しているとき `[43]` `[44]` がどちらも `01` になることを、`watch` サブコマンドの実機ログで確認した。

例（左だけ接続）：`… 14 02 10 02 00 04 03 FF FF FF 00 "1067939" 00 "1067939" 00 "0000000" 00 01 FF BB`

文字列はファームウェアを 02.000.006 から 03.000.004 に更新しても `1067939` のままだったので、ファームウェアのバージョンではない。何の値かは分かっていない。

## 4. `14 04` バッテリー

自発送信と、問い合わせ（`41 04`）への応答の両方で届く。どちらも同じ形式。自発送信は、イヤホンを出し入れしたときと、残量が 1% 変わったときに届く。

| オフセット | 値 | 意味 |
|---|---|---|
| `[14]` | 0–100 / `0xFF` | 左（%）。`0xFF` は未接続 |
| `[16]` | 0–100 / `0xFF` | 右（%）。`0xFF` は未接続 |
| `[18]` | 0–100 | ケース（%）。片耳でも接続していれば取れる |

例：`02 12 04 FF 0F 00 96 C3 14 04 10 01 00 00 63 00 64 FF 64 AC`（L 99% / R 100% / ケース 100%）

## 5. `14 03` ファームウェアのバージョン

`[13..24]` に 4 バイトずつ 3 組。並びは **左 / USB トランシーバー / 右**（`14 02` とは並びが違う）。未接続のイヤホンは `FF FF FF FF`。

| INZONE Hub の表示 | 1 組のバイト列 |
|---|---|
| 02.000.006 | `02 00 60 00` |
| 03.000.004 | `03 00 40 00` |

先頭のバイトがメジャーバージョン、3 バイト目の上位 4 ビットが末尾の番号に対応していそうだが、正確な符号化は分かっていない。

## 6. 意味が分かっていないレポート

| 種別 | 観測した本体 | 備考 |
|---|---|---|
| `14 21` | `[13]=00 [14]=0C [15]=FF` | 左右どちらの接続でも同じ値 |
| `14 41` | `[13]=00/01/02 [14]=14 [15]=FF [16]=00` | 両耳が接続している間に、`[13]` が `01` → `02` → `00` と変わりながら自発的に届いた。装着検知の可能性がある（未確認） |

## 7. ドングルが制御要求に応答しなくなる状態

次の症状が続く状態を一度観測した。PC を再起動し、INZONE Hub を入れ直し、ドングルを別の USB ポートに挿し直したところ直った。どれが効いたのかは分かっていない。

- `HidD_GetProductString` などの文字列の要求が、毎回約 5 秒でタイムアウトする
- 問い合わせの `WriteFile` が戻らない（40 秒以上）
- 再生デバイスの名前が「INZONE Buds - Game」ではなく「ヘッドホン (USB Audio Device)」になる
- 自発送信のレポート（`12 01` / `14 xx`）は届く。音も出る

この状態でもアプリが止まらないよう、次の 2 点を守る。

- 列挙のときに文字列の要求をしない。hidapi は列挙や初期化のときに文字列を要求するため、使わない
- 問い合わせの送信にはタイムアウトを付ける（Overlapped I/O）

## 8. 再生デバイスの状態

両耳をケースに戻しても、ドングルの再生デバイスは 2 つとも「アクティブ」（`DEVICE_STATE_ACTIVE`）のままだった。そのため、再生デバイスの状態は接続/切断の検知には使えない。

## 9. INZONE Hub との共存

INZONE Hub 1.0.20.0 が起動している状態でも、`FF04:0001` を共有モード（`FILE_SHARE_READ | FILE_SHARE_WRITE`）で開き、問い合わせを送って応答を読めた。probe が 10 秒ごとに問い合わせている間も、Hub の表示（接続とバッテリー）は正常で、イヤホンの出し入れにも追従した。

## 10. ドングルの抜き差し

- 抜くと、開いていたすべてのハンドルの `ReadFile` / `WriteFile` が `ERROR_DEVICE_NOT_CONNECTED`（`0x8007048F`）で失敗する
- 挿し直しても、古いハンドルは失敗したまま。列挙し直して開き直す必要がある

## 11. スリープからの復帰

- スリープ中も、開いたハンドルは有効なまま。復帰後に開き直す必要はない
- スリープ前に送った問い合わせや、復帰直後に送った問い合わせには応答がなかった
- 復帰の約 7 秒後に、自発送信の `12 01` が届いて現在の状態が分かった。その後の問い合わせには普通に応答した
